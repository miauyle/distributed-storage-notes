# Failure Model / Timeout：远端发生了什么？

[Read / Write Path](../03-object-storage/03-read-write-path.md)区分了数据就绪、状态发布和响应送达。本篇把其中的故障问题抽出来：**一次请求没有按时返回，究竟是没有执行、正在执行，还是已经提交但丢了响应？**

本文采用通用工程模型，讨论节点崩溃、不可达、延迟和消息丢失，不假设恶意节点。时间线与状态表是示意，不描述 AWS S3 或其他产品的内部实现，也不展开形式化证明。

## 1. Partial Failure：系统没有共同的“全部成功或全部失败”时刻

单进程代码往往能在同一执行上下文中判断函数是否完成。分布式请求跨越网络、进程和持久层，其中一部分可以正常工作，另一部分可以失效；各参与者还可能拥有不同观察。

例如 Gateway 仍能接收请求，数据节点已经持久化正文，Metadata 的提交调用却没有返回。客户端只看到了失败响应或超时，无法据此把其他参与者的状态一起清零。这就是 Partial Failure（部分失败）需要处理的核心：**局部失败并不自动撤销已经发生的远端效果。**

[Replication 的 Write ACK](../07-data-protection/01-replication.md)同样有这个边界：某节点未返回 ACK，可能尚未完成，也可能已达到持久化条件但响应丢失。发送了几份请求、收到几份 ACK、实际上留下几份数据，是不同事实。

## 2. 故障类型先描述现象，再判断后果

| 情形 | 实际可能发生什么？ | 观察者容易误判什么？ |
| --- | --- | --- |
| Node Crash | 进程或主机停止执行，内存状态可能丢失 | 把进程崩溃直接当作持久数据全部丢失 |
| Temporary Unavailable | 重启、维护、资源耗尽等使服务暂时无法响应 | 把暂时不可用当作永久退出 |
| Network Partition | 某些节点之间不能通信，节点本身可能继续运行 | 把自己联系不到的节点当作对所有人都失效 |
| Slow Node | 排队、I/O 阻塞、调度或运行时暂停使响应变慢 | 超时后认为它不会继续执行旧请求 |
| Request Loss | 请求未到达目标处理入口，或连接在传输中断开 | 单凭没有响应就认定请求一定丢失 |
| Response Loss | 请求已执行，返回消息丢失或连接断开 | 把丢失响应等同于丢失业务效果 |

这些情形不是互斥标签。一个节点可以因设备 I/O 变慢而触发请求超时，随后重启；网络分区还可能只影响特定方向或连接。TCP 的重传和连接管理也不能把“远端业务是否提交”变成客户端总能知道的事实。

描述故障时最好带上观察主体和范围：“Gateway G 无法联系 Node A 的数据接口”，比“Node A 已死”更准确。心跳端口可达，不证明正文写入路径健康；正文还在，也不证明鉴权、元数据和提交路径可用。

## 3. Timeout 是等待预算耗尽，不是服务端执行判决

Timeout 表示某个观察者在规定时间内没有获得所需结果。这个时间界限首先是资源和延迟管理策略：客户端不能无限占用连接、线程和业务等待时间。

以下为一种已经提交却超时的执行，T0～T4 只表示事件先后，不是跨机器同步时钟的证明：

| 时刻 | Client | Server / 网络 | 客户端拥有的证据 |
| --- | --- | --- | --- |
| T0 | 发出操作 O，开始等待 | 请求进入传输 | 操作已尝试发送 |
| T1 | 继续等待 | Server 收到 O 并执行 | 尚无确定结果 |
| T2 | 继续等待 | O 已提交，Server 生成成功响应 | 客户端还不知道提交事实 |
| T3 | 没收到响应 | Response 丢失或连接断开 | 仍无确定结果 |
| T4 | Client Timeout，结束本次等待 | O 的效果仍已提交 | 等待超时；提交结果未知 |

客户端相同的超时观察，还可以对应“请求未到达”“正在排队”“执行到一半”“已提交但响应延迟”等其他过程。**仅凭 T4，客户端不能倒推出 T1～T3。**

超时通常也不是取消协议。关闭连接、停止等待，未必使服务端停止；即使发送 Cancel，也需要协议明确取消何时生效、与提交如何协调、取消结果是否确定。检查本地 deadline 不能撤销此前已发出的远端请求。

## 4. Failure、Timeout 与 Unknown Result 分别属于哪一层？

| 概念 | 描述对象 | 能据此做出的判断 |
| --- | --- | --- |
| Failure | 某组件、通信路径或操作未满足要求 | 需要进一步说明失败范围、持久状态和接口保证 |
| Timeout | 某次等待在截止时间前未获得预期结果 | 本次等待结束，不能单独证明操作没有执行 |
| Unknown Result | 某观察者缺少足够证据判定操作的最终结果 | 保留操作身份，按契约查询、重试或交由后续判定 |

Unknown Result 是知识状态，不是服务端必须有的业务状态。服务端可能已经明确提交，只有客户端不知道；也可能服务端自己尚需从可恢复记录中判定提交结果。

若客户端能确证请求从未发出，例如本地参数校验在任何发送前拒绝操作，可以判断这次尝试没有远端效果。但请求可能出站以后，仅凭一次断连、服务错误或 Timeout 通常不足以作同样判断；错误是否保证“未提交”，必须由具体接口定义。

查询也有身份边界：GET / HEAD 返回的是当前对象状态，未必说明操作 O 的历史结果。后来被覆盖的数据可能掩盖先前成功，当前内容相同也可能由另一个请求写入。[S3 Core Semantics](../03-object-storage/02-s3-core-semantics.md)已有相应 Timeout / Retry 例子，本篇不重复操作语义。

## 5. 不可达与永久丢失，为什么需要分开？

Node A 不可达时，可能发生了三种不同情况：数据仍在但网络不通；节点需要重启而持久数据仍可恢复；唯一介质已永久损毁。当前观察相同，数据后果不同。

因此应区分：

- **访问不可用：**目前无法取得需要的数据或执行操作。
- **保护余量下降：**当前可用的合格副本 / 分片少于目标布局。
- **永久数据丢失：**所需状态已经没有足够的有效持久来源恢复。

不可达会限制服务能力，并可能触发保护策略，却不能仅靠一个超时直接证明第三项。反过来，节点重新上线也不证明它拥有最新已提交状态；资格还取决于数据身份和持久化条件，见[Replication](../07-data-protection/01-replication.md)。

## 6. Failure Detection：根据证据作决策，仍要处理误判

Failure Detector 可以观察心跳、请求结果、连接状态和其他信号，将节点标记为 suspected、unavailable 等状态。它要支持及时决策，但在没有可靠延迟上界时，有限等待很难区分“已经停止”和“仍在运行但很慢”。

多个观察者可能得到不同结论。连续丢失心跳提高怀疑程度，不构成“该节点已经不能再写”的资源侧保证；撤掉路由也可能无法阻止其已经发出的写入。后者需要[下一篇的 Ownership 与 Fencing](02-quorum-leader-lease-fencing.md)。

| 判断倾向 | 可能收益 | 工程代价 |
| --- | --- | --- |
| 更快怀疑故障、缩短等待 | 更快避开失效路径，减少等待占用 | 慢节点容易被误判，增加切换、重复工作和额外流量；错误切换还可能留下两个自认为有资格的执行者 |
| 更慢怀疑故障、延长等待 | 减少短暂抖动导致的切换 | 真实故障响应变慢，积压连接和请求；保护缺口可能更久未被处理 |

请求 Timeout、节点故障判定阈值、Lease 到期时间服务于不同目标，不能直接用一个值替代全部配置。Timeout 的覆盖范围也要明确：连接建立、排队、正文传输、提交等待是否包含在同一预算内。延迟分布、负载和网络范围变了，原有阈值的误判率也会改变。

## 7. 从“知道什么”走向“允许做什么”

发现远端可疑后，系统仍需回答：可否改选写入者？旧执行者是否会继续写？新执行者能否重复旧任务？

三篇依次分开这些职责：本篇解释故障观察与未知结果；[Coordination / Ownership](02-quorum-leader-lease-fencing.md)解释当前修改资格及旧执行者隔离；[Retry / Idempotency](03-retry-idempotency-deduplication.md)解释同一意图再次提交后的状态与副作用。故障检测策略不是后两者的替代品。
