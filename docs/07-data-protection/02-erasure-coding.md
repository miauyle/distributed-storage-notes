# Erasure Coding：减少冗余字节，把成本放在哪里？

[Replication](01-replication.md)用多份完整数据提供保护。如果保护 1 PiB 正文需要三份副本，仅正文就占约 3 PiB；随着数据规模扩大，容量、设备和传播成本会成为架构约束。**能否保留足够的恢复信息，而不重复保存每一份完整正文？**

Erasure Coding（EC，纠删码）将一组数据编码成多个分片，使部分分片缺失时仍能恢复原数据。本文采用 **systematic MDS 的 k+m 模型**，例如常见 Reed-Solomon 类编码：保留 k 个原始数据分片，生成 m 个校验分片，任意 k 个有效分片可恢复原数据。并非所有 EC 都具有“任意 k 个”性质；本篇数字结论限定在这个模型内，不展开数学构造或具体产品实现。

## 1. 先分层：编码的不是 Multipart 协议身份

沿用[Object Layout](../03-object-storage/06-object-layout.md)的映射，不重复其分块与聚合机制。下表只标明保护机制接在哪一层。

| 概念 | 所属层与职责 | 不应混同的关系 |
| --- | --- | --- |
| Object / Object Version | API 层可寻址的正文状态 | 一个版本不是一个 EC Fragment |
| Multipart Part | 上传会话内的准备资源，按 Upload ID / Part Number 管理 | Part 边界不规定编码边界，Complete 不规定某种 EC 布局 |
| Internal Storage Unit | 布局层管理的单元，可能对应对象的一段或聚合区域 | 一个单元可以包含多个编码 Stripe；不是所有实现都采用同一种单元粒度 |
| Replica | 某个被保护状态的完整副本 | 是完整拷贝，不是编码组中一个部分数据分片 |
| EC Fragment | 编码组内的数据或校验分片，有组身份、位置及状态身份 | 不能独立当作完整对象，也不能仅按节点数判断其可恢复性 |

本篇用一个 U 的 16 MiB 区域构成一个 Stripe。其他实现可以把一个 U 编成多个 Stripe，或让编码组覆盖其他内部布局范围。Object → Internal Storage Units → Protection Groups 是理解职责的通用链条，不是强制的数据库层级。

## 2. k+m、Data Fragment、Parity Fragment 与 Stripe

Stripe 指共同编码和恢复的一组对应数据区域及其校验区域；本文将其中每个区域称为 Fragment。系统文档中 chunk、shard、strip 等名称可能不同，阅读时需核对粒度。

**4+2 示例：**把 U 的 16 MiB 分为四个 4 MiB Data Fragment，再由它们计算两个 4 MiB Parity Fragment。原始数据保留在 D1～D4，P1 / P2 各自保存一组恢复关系，不是某个 D 的简单备份，也不是完整 U。

| Stripe S / generation g1 | 内容 | 大小（示意） | 正常读取时的角色 |
| --- | --- | --- | --- |
| D1 | U 的 `[0, 4 MiB)` | 4 MiB | 直接提供对应原始字节 |
| D2 | U 的 `[4, 8 MiB)` | 4 MiB | 直接提供对应原始字节 |
| D3 | U 的 `[8, 12 MiB)` | 4 MiB | 直接提供对应原始字节 |
| D4 | U 的 `[12, 16 MiB)` | 4 MiB | 直接提供对应原始字节 |
| P1 | 由 D1～D4 计算的校验信息 | 4 MiB | 缺失分片时参与恢复 |
| P2 | 另一组独立校验信息 | 4 MiB | 缺失分片时参与恢复 |

所有参与恢复的分片必须属于同一个 Stripe 和相容的 generation。六个名字相同却混有旧、新写入状态，不构成一个有效的 4+2 编码组。

## 3. Storage Overhead 与容错预算怎么计算？

忽略元数据、对齐、日志、临时数据和布局空洞，原始正文为 k×F，编码后为 (k+m)×F，其中 F 为分片大小。

- **占用倍数** = (k+m)/k。4+2 为 1.5，即 16 MiB 正文占 24 MiB。
- **额外冗余比例** = m/k。4+2 为 50%。“开销 1.5 倍”与“额外开销 50%”是不同表达，不能混用分母。
- 在本篇 MDS 模型中，完整且有效的编码组能容忍任意 m 个分片缺失；4+2 为最多两个。

缺失 D1 / D2，或缺失 D1 / P1，或缺失 P1 / P2，都仍有四个有效分片，原始数据可恢复。若同一 Stripe 丢了三个，就不能保证完整恢复；某些尚在的原始范围仍可能能读，但不代表 U 的全部字节可重建。

这里的 Failure 是**分片擦除，即知道哪些分片缺失或不可用**。不能把 m 直接解释为任意未知字节错误的纠正能力，也不能直接解释成 m 个 Rack / AZ 失效。节点或机架一次带走几个分片，由[Failure Domain & Placement](03-failure-domain-placement.md)决定。

此外，数据可恢复需要正确的组身份、布局与编码参数。正文分片尚在而关键映射不可恢复，用户仍可能无法读取对象。EC 正文保护不替代元数据的保护与提交要求。

## 4. Encode 与写入确认：可解码不等于达到目标保护

Encode 从同一组数据计算校验分片，再按布局将数据与校验分片写到目标位置。编码可以流式处理，不要求先把整个 Object 收齐在一台机器的内存中。

一种通用写入模型为：确定 Stripe / generation → 形成相容的数据与校验 → 写入分片并收集符合持久化条件的 ACK → 检查保护要求 → 提交引用。步骤可以流水化或合并，但不能把不相容状态拼成“已经达到门槛”。

Replication 的“一份副本就是完整数据”在这里不成立。对已确认持久化的 a 个相容 MDS 分片，若 a≥k，字节层面可恢复；在其他尚未确认分片完全不可依赖的保守模型下，再失去 a−k 个分片后仍可恢复。

| 4+2 中已确认有效分片 a | 此刻的字节条件 | 按分片丢失计的剩余余量 |
| --- | --- | --- |
| 4 | 有足够信息恢复原数据 | 0；再丢一片就不能保证恢复 |
| 5 | 可恢复，但未达到六片目标 | 1 |
| 6 | 达到完整编码布局 | 2 |

因此 **“收齐 k 个 ACK 就可以解码”不等于“此刻已兑现 m 个分片容错”**。系统若允许缺片确认，必须明确降低后的承诺，或依赖其他已达到要求的持久层；不能把尚未完成的目标分片算进当前预算。

这仍只是正文数据条件。对象完整可见性、多个 Stripe 的提交和失败写入判定，需要兑现[Read / Write Path](../03-object-storage/03-read-write-path.md)中的发布边界。若数据更新后旧校验仍被当作 g1 使用，正常读可能暂时成功，却在首次缺片时暴露错误。

## 5. 正常读与 Degraded Read 的成本为什么不同？

Systematic 编码保留原始数据。完整读取示例 U，通常可读取 D1～D4 并拼接；只取 D2 的某个范围，在布局、校验和 I/O 粒度允许时，可以只读相应区域，不必每次都读六片或执行 Decode。

Degraded Read 指所需原始字节的直接来源不可用，需要从其他有效分片恢复。假设 D2 不可用，D1 / D3 / D4 / P1 可用，它们共同提供恢复 D2 的信息。P2 可以成为替代来源；不是要求优先固定某个校验分片。

| 请求情形 | 示意读取方式 | 增加的成本 |
| --- | --- | --- |
| D2 可用，读取其中 64 KiB | 直接读取 D2 对应范围 | 取决于设备、缓存与校验粒度 |
| D2 缺失，实现支持对应范围解码 | 读取四个有效分片各自对应的 64 KiB 编码范围 | 本例读取 256 KiB 来恢复 64 KiB，另有解码与请求开销 |
| D2 缺失，实现只能按整片处理 | 读取四个各 4 MiB 分片 | 为小范围请求读入更多字节，延迟与内存开销更大 |

这些是两种可能的解码粒度，实际还受编码对齐、索引和校验约束影响。EC 不必天然按整个对象解码；正常 Read amplification 也不能只用 k 或 k+m 定义。

即使仅 P1 不可达，D1～D4 的正常读仍可能不变，但整个组已处于保护缺口。本篇沿用 Replication 中 Degraded 的描述性含义；Degraded Group 与需要 Decode 的 Degraded Read 不等价。

## 6. Reconstruction：恢复字节与恢复布局分开理解

缺失分片的基本重构过程是：

1. 确定缺失分片的 Stripe、位置、generation 和编码参数。
2. 取得足够数量的相容有效分片，排除已识别的不合格来源。
3. Decode 得到所需字节，或计算缺失的校验分片。
4. 若目标是恢复保护布局，还需将结果持久化到合格位置并确认布局状态；仅为读请求返回恢复字节，不等于已经补齐持久分片。

以传统整片读取的 4+2 示例，重构一个 4 MiB 缺失分片可以读取四个有效分片共 16 MiB，再写出 4 MiB。相比复制一个 4 MiB 的同大小完整副本，EC 需要汇集多个来源和编码计算。这是按**待补齐字节**计的基本成本，不是所有 EC 算法的带宽下界；优化编码、子范围处理与一次补多片会改变数值。

本节只给出重构字节的机制边界与成本。任务调度、检查点、限流、失败重试及完整节点 Rebuild 流程留给[后续 Repair / Rebuild 规划](README.md)，不在此展开。

## 7. Small Write / Partial Update 为什么更复杂？

校验依赖一组数据，所以部分数据变化会使相关校验也变化。若直接把 D2 的某个区域从旧值改成新值，同时没有更新 P1 / P2，编码组就失去一致的恢复关系。

通用实现可选的方式包括：

- **写完整新 Stripe。** 重新形成一致的数据与校验后发布引用，易于解释状态，但小改动可能引发较多写入。
- **Read-modify-write。** 读取所需旧数据或校验，计算更新后内容，再协调相关片的写入；读取、校验更新与故障提交带来额外复杂度。
- **先聚合或使用独立暂存持久层。** 把小写组织为较完整编码输入；需要处理等待、额外空间和后续转换责任，最终 EC 成本不会凭空消失。

这些是设计选项，不是规定每次更新必须读取整个 Stripe。旧数据、新数据和校验之间的相容状态，需要通过日志、状态身份或其他协议保护；本篇不指定事务或恢复算法。

Small Write 还不等于 Partial Update：一个新建小对象可能只是填不满编码粒度，承受补齐、对齐和固定开销；Partial Update 则改变已存在编码数据的一部分。应用按 PUT 重新提交完整对象，又是 API 更新粒度，不能把这些层次混为一种写放大。

## 8. 与 Replication 比较，要在相同口径下看工作负载

以下比较三副本与本篇 4+2，在布局完整、均以正文计量、每份副本或分片位于独立故障来源的示意条件下。两者字节层面都可承受任意两个对应来源失效，但这不是相同年持久性或相同机架容错的保证。

| 维度 | 三副本 | 4+2 EC | 工程取舍 |
| --- | --- | --- | --- |
| 容量 | 正文约 3 倍 | 正文约 1.5 倍 | EC 节省容量，但不能忽略小对象对齐与元数据等成本 |
| CPU / 内存 | 无纠删码计算，仍有复制、校验等处理 | 增加 Encode；缺片时增加 Decode 与缓冲 | 是否成为瓶颈取决于编码优化、硬件与并发 |
| 完整写入 | 最终保存约 3S 正文 | 最终保存约 1.5S 编码字节 | EC 减少字节却涉及更多分片端点；实际网络量还依赖拓扑和重试 |
| 正常读取 | 一个合格副本可提供某单元完整字节 | 对应 Data Fragment 可直接读，完整组需拼接数据片 | EC 并行度可能更高，也增加协调；小范围读不能一律按全组算 |
| 写入延迟 | 取决于 W、持久化和提交路径 | 增加编码、分片确认及可能的输入聚合 | 不能从容量倍数推导延迟倍数，需按目标保护条件比较 |
| 故障读取与补齐 | 切换合格完整来源或复制缺失数据 | 汇集相容分片并解码 | EC 在传统重构方式下消耗更多来源 I/O，故障时更容易与前台争用 |

大对象顺序写入可更好摊薄 EC 的固定成本；小而频繁的更新则更敏感于编码粒度和提交协调。选择方案需要结合容量预算、读写分布、尾延迟及故障期间资源余量，而不能只按 3 倍与 1.5 倍做决定。

接下来问：六个 Fragment 或三个 Replica 到底放在哪里？如果一次机架故障带走了超过预算的分片，编码数学就无法兑现原来的保护目标。下一篇进入[Failure Domain & Placement](03-failure-domain-placement.md)。
