# Latency / Throughput / Queueing：成本如何变成等待

[上一篇](01-end-to-end-cost-model.md) 定位了工作与等待可能发生的地方。本篇回答：为什么提高并发先能增加吞吐，后来却主要增加排队？为什么 Average Latency 看起来不错，部分请求仍然很慢？

以下是面向存储请求的通用工程模型，不推导完整 Queueing Theory，也不把一个资源的利用率当成所有系统的饱和阈值。

## 1. 指标首先要带上边界和单位

| 指标 | 本篇的含义 | 比较前必须说明 |
| --- | --- | --- |
| Latency | 指定起止点的经过时间，通常包含处理与等待 | API 全响应、首字节、某次 RPC 或设备操作？是否包括重试？ |
| Throughput | 单位时间完成的工作量 | 有效请求 / s、操作 / s，还是有效正文字节 / s？是否只计成功？ |
| Bandwidth | 数据传输能力或实际传输速率；需注明是哪一种 | 标称链路、实测网卡、应用正文还是设备字节？ |
| IOPS | 指定 I/O 层每秒完成的操作数 | 设备、块层或其他 I/O 层；不能直接拿 API requests/s 替代 |
| Concurrency | 某边界内同时在途的工作数 | 是配置上限、瞬时数量还是时间平均？包括等待中的请求吗？ |
| Queue Depth | 指定队列边界内的工作数量 | 有的口径仅含等待，有的含已发出但未完成 I/O；应查明工具定义 |
| Utilization | 资源忙碌程度或占用比例 | 按核、节点、容器额度还是共享链路统计？分母是什么？ |
| Saturation | 当前需求接近或超过某项可服务能力，继续增加工作主要形成等待或拒绝 | 与请求组成、调度、资源范围相关，不要求所有仪表都显示 100% |

应用一次 GET 可能产生多个设备 I/O，也可能因缓存完全不触及设备。应用并发、RPC 在途数、设备 Queue Depth 不一定相同。把设备 IOPS 和对象 requests/s 混用，会在请求大小或布局改变后得出错误结论。

固定大小、同一操作集合中，有效 bytes/s 可由完成数乘请求有效字节数计算；混合大小请求应加总实际完成的有效字节，不能拿一个未定义的“平均对象大小”跨测试比较。

## 2. 从低并发到 Saturation：更多在途工作不总是更多有效工作

以下阶段表是示意趋势，不是所有系统必定出现的曲线；顺序依赖、访问局部性和请求组成也会改变趋势。

| 阶段 | 提高并发后可能发生什么 | 应如何解释 |
| --- | --- | --- |
| 低并发 | Throughput 上升，Latency 变化不大 | 更多独立请求填补 CPU、网络或 I/O 空隙；尚有可用服务能力 |
| 接近限制 | Throughput 仍上升但增幅变小，等待开始增加 | 某项资源或执行资格接近限制，新增请求需要排队 |
| 已 Saturated | Throughput 增长有限，Queue 与 Tail Latency 快速上升 | 新增在途工作主要变成等待，不是新增完成能力 |
| 过度竞争 | Throughput 可能下降，错误或 Retry 增加 | 争用、调度开销和重复工作又消耗预算；应确认实际机制 |

利用率不高也可能存在局部饱和：一个处理线程、一个 Metadata Partition 或一条内部链路可以先受限，节点总体平均却仍有余量。反过来，持续繁忙但队列稳定、目标吞吐和延迟满足要求的资源，不必仅因“很忙”就被判为待优化瓶颈。

配置并发是准入或发送能力，实际 Concurrency 是运行事实。客户端数据准备、连接池限制、请求间隔及其他阶段等待，会使实际在途数量低于配置值；不能把参数设成某个数就当作系统已承受相同数量的有效请求。

## 3. Little’s Law：三个平均量要来自同一集合

Little’s Law 用平均在途数量、平均速率与平均停留时间建立联系：

```math
L = \lambda W
```

在本篇选择的边界内，`L` 是包括处理与等待的时间平均请求数，`λ` 是请求平均到达率，`W` 是请求在该边界内的平均停留时间。对可稳定统计、没有持续积压增长的工作集合，足够长窗口内的进入和完成速率相匹配，可用同口径完成速率作工程估算；短窗口还需注意跨窗口的在途请求。

**算术示意，非实测性能：**同一稳定请求集合每秒完成 1,000 个请求，平均停留 10 ms，则平均在途数量约为 10。若完成能力仍为 1,000 / s，而平均停留变为 50 ms，则相应平均在途约为 50；更多数量可能只是更多等待。

这不是“把并发设为 50 就能达到某个吞吐”的预测。`L` 是实际时间平均量，不是配置上限；`W` 是平均值，不是 P99；`λ` 的单位是所选工作 / s，不是网络 GB/s。它也不能仅靠这三个量指出瓶颈在哪个资源。

还要保持集合一致：如果 `L` 包含所有已接收请求，速率和停留时间也要按相应终止状态处理，不能只用成功请求的 Throughput。客户端 Timeout 后，服务端可能仍在执行；客户端的请求生命期与服务端的工作生命期因此不同，不能混入同一个公式。故障语义回看 [Timeout / Unknown Result](../06-distributed-systems/01-failure-model-timeout.md)。

## 4. Average、P50、P95、P99 回答不同问题

Average Latency 是请求样本的平均时间；P50 / P95 / P99 是相应延迟分布的分位位置，描述典型请求与尾部。应写清请求类型、样本集合、窗口和统计方法；P99 不是最大值，也不是“99% 可用性”。

示意一组 1,000 个完整请求：980 个耗时 1 ms，20 个耗时 100 ms，Average 为 2.98 ms，P99 位于 100 ms 的尾部。这只是人为构造的分布，说明平均数会隐藏少部分长等待，不代表任何系统的延迟。

不同请求大小、读写类型或失败结果混在一起，可能让平均值失去解释力。快速失败会使混合 Average 下降，却不能证明有效服务变快；慢错误同样应记录，而不是简单丢弃。性能结果需要同时报告成功、错误和相应延迟。

跨客户端合并结果时，应合并原始样本或可正确合并的直方图，再算全局分位数，不能平均各 Client 的 P99。样本太少或测试太短，P99 会很不稳定；重复窗口和请求数是解释尾延迟的条件，不是附加装饰。

## 5. 分布式等待条件怎样放大 Tail Latency

慢 CPU、排队的 RPC、慢设备或共享链路，只有进入本次请求的依赖路径，才会影响本次完成时间。组合关系取决于拓扑和等待规则：

| 请求组合 | 完成时间受到什么影响 | 不能推出什么 |
| --- | --- | --- |
| 串行依赖 | 各必要阶段的处理与等待沿依赖链累积 | 各阶段 P99 不能简单求和为系统 P99 |
| 并行且等待全部必要结果 | 本次必要分支中最后一个完成事件，加上前后公共阶段 | 系统 P99 不等于“最慢节点的 P99” |
| 并行且等待足够数量的合格结果 | 达到门槛所需的完成事件及选择规则 | 不能无条件按全部分支的最大耗时计算 |
| 具有共享瓶颈或相关干扰 | 多个分支可能一起排队或变慢 | 不能默认下游延迟相互独立 |

一个限定的概率示意：四个必要分支并行，必须全部完成，各自独立且同分布，在阈值 t 内完成的概率均为 99%。那么全部在 t 内完成的概率为 `0.99^4`，约 96.06%，超过 t 的概率约 3.94%。阈值未变，等待更多必要结果已改变整体分布；这是明确假设下的算术推导，不是产品性能，也不适用于相关故障或不同门槛。

实际存储还有公共 Gateway、多个数据单元、分片与返回拼接等关系。分布式 Fan-out 的影响需要按真实依赖和相关性判断，不能拿一个节点的百分位替代端到端分布。

## 6. 保护与后台工作改变等待，不只改变容量

并行 [Replication](../07-data-protection/01-replication.md) 中，ACK 数量和合格条件改变返回所需的完成事件；提高门槛可能更依赖慢来源，但不意味着延迟按 ACK 数线性倍增。后台传播仍影响资源，即使某份 ACK 不在本次关键路径中。

[EC](../07-data-protection/02-erasure-coding.md) 的 Encode、分片写入以及适用的 Decode，会增加 CPU、内存与下游 I/O。正常读、Degraded Read 和不同范围请求的等待条件不同，不能从 `k+m` 直接算出固定延迟比例。

Recovery / Rebalance 的背景流量可能让原有服务时间大致不变，而 Queue Waiting 增加，也可能因争用改变实际服务时间。应记录后台状态和预算，回看 [Recovery 资源协调](../10-recovery-operations-observability/03-recovery-task-coordination.md)，不在此展开 Foreground / Background Interference 专题。

## 7. Bottleneck Shift：限制会随工作负载和改动移动

Disk → Network → CPU → Metadata → Queue 可以表示一条示意的瓶颈迁移链，不是固定优化顺序，也不是五种互斥原因。Queue 常是某项限制的表现，本身还可能受并发或准入策略约束，需要继续找“等待什么”。

例如减少设备等待后，大对象传输可能开始受网络限制；网络成本降低后，校验与内存处理更显眼；切换成大量小请求后，Metadata 或 per-request CPU 又可能成为主导。优化前的瓶颈结论不能自动沿用到下一种 workload。

本篇把成本连接到吞吐与等待，但仅观察这些关系仍不能完成归因。下一篇通过 [Benchmark / Bottleneck Analysis](03-benchmark-bottleneck-analysis.md) 建立可重复、可反驳的实验判断。
